## v1.4 추가 모듈 (구직 효율화)

| 모듈 | 역할 |
|---|---|
| `scoring.py` | 공고 점수화: 직군 가중치×10 + 제목 스킬(+5/개) + 워치리스트(+30) + 신규(+10) + 마감 D-3(+5). `is_noise()`로 제외어 필터 |
| `history.py` | SQLite 이력 DB (`jobs_history.db`). `ingest()` upsert → (신규 링크, 처음 보는 회사) 반환. `canonical_link()`로 사람인 링크 rec_idx 정규화(중복 방지). 반복채용/신규회사/주간통계 쿼리 제공 |
| `jd_match.py` | Top 공고(최대 12건)의 상세 페이지를 열어 `MY_SKILLS` 매칭. 실패 시 None (알림은 계속 진행) |
| `weekly_report.py` | 이력 DB 기반 주간 리포트 md 생성 → `ob_storage`(Obsidian) 저장 + 슬랙 알림. 스케줄: `JobScope_Weekly_Report` (매주 월 09:00) |

v1.4 데이터 흐름: `run_all`(크롤링+노이즈필터+기본점수) → `history.ingest`(신규 판정) → `scoring`(신규 가점 재계산) → `jd_match`(Top 10만) → 슬랙 (⭐워치리스트 신규 + 🏆Top 10). 대시보드는 `점수`/`워치리스트` 컬럼으로 추천순 정렬·⭐뱃지, localStorage로 북마크/지원함 관리.

## 3. 모듈 명세

### 3.1 config.py — 공통 설정
- `KEYWORDS: dict[직군, list[키워드]]` — 8개 직군(IBD, 회계/CPA, CFA, 애널리스트, 증권, 컨설팅, AI, AX/DX) 총 36개 키워드
- `KEYWORD_TO_CATEGORY` — 키워드 → 직군 역매핑 (통합 시 `직군` 컬럼 생성에 사용)
- `ALL_KEYWORDS` — 중복 제거된 전체 키워드 리스트
- `MAX_PAGES` — 키워드당 최대 페이지 수. 환경변수 `MAX_PAGES`로 오버라이드 (기본 10)

### 3.2 크롤러 3종 (공통 인터페이스)
모든 크롤러는 `crawling_data(keyword, max_pages) -> list[dict]`를 제공한다.

| 모듈 | 대상 | 방식 | 페이지당 | 특이사항 |
|---|---|---|---|---|
| `saramin.py` | 사람인 `zf_user/search` | requests+bs4, `recruitPage` 페이징 | 40건 | 직무분야 끝의 "등록일 YY/MM/DD"를 게시일로 분리 |
| `work24.py` | 고용24 `retriveDtlEmpSrchList.do` | requests+bs4, `currentPageNo` 페이징 | 10건 | 마감일은 행 옆 `<script>`의 `var date` 정규식 추출 |
| `linkedin.py` | LinkedIn 게스트 API `jobs-guest/.../search` | requests+bs4, `start=n*25` 페이징 | ~25건 | 로그인 불필요. 429 시 5초×시도횟수 대기 후 재시도(3회) |

공통 정책:
- 요청 간 `time.sleep(2)` (사이트 예의)
- 결과 없으면 조기 종료 (`break`)
- `clean_text()`: html unescape + 연속공백 정리

### 3.3 run_all.py — 통합 실행기
- `ThreadPoolExecutor(max_workers=3)`로 **소스 3개를 병렬** 크롤링
  (사이트별 요청 간격 2초는 스레드 안에서 유지되므로 각 사이트 부담은 순차 실행과 동일)
- 소스별 dedup(링크 기준) → `직군` 컬럼 매핑 → 소스별 csv/json 저장
- 통합: 공통 컬럼 `[출처, 직군, 검색어, 공고 이름, 회사 이름, 회사 위치, 게시일, 마감일, 링크]`로 정렬 후 `all_jobs.csv/json` 저장
- `main()`이 통합 DataFrame을 반환 (run_and_notify가 재사용)

### 3.4 server.py — 대시보드 서버 (FastAPI, :8010)
- 정적 서빙(StaticFiles) + 크롤링 API (상세는 [API명세서.md](API명세서.md))
- 크롤링은 서브프로세스(`python run_all.py`)로 실행, 상태는 메모리 `state` dict + `crawl_log.txt`
- no-cache 미들웨어: `/`, `*.html`, `*.json` 응답에 `Cache-Control: no-store`
  (브라우저 휴리스틱 캐싱으로 옛 화면/데이터가 보이던 문제의 재발 방지)

### 3.5 run_and_notify.py — 스케줄 실행 + 슬랙 알림
1. 크롤링 전 `all_jobs.json`의 링크 집합 스냅샷
2. `run_all.main()` 실행
3. 신규 공고 = 새 결과 − 스냅샷 (링크 기준)
4. 슬랙 메시지 전송: 총건수, 소스별 건수, 신규 N건 + 미리보기 5건(링크)
5. 예외 발생 시에도 슬랙으로 실패 알림 후 re-raise (스케줄러 이력에 실패 기록)
- 웹훅 URL 조회 순서: 환경변수 `SLACK_WEBHOOK_URL` → `slack_webhook.txt` → 없으면 알림 생략(크롤링은 정상 수행)
- `os.chdir(BASE_DIR)` — 작업 스케줄러의 cwd(System32) 문제 방지

### 3.6 job_board.html — 대시보드 (SPA, 바닐라 JS)
- 데이터: `all_jobs.json` (`cache: no-store`) → 없으면 `linkedin_result.json` 폴백
- 필터: 공고 출처(3) × 직군(8) × 지역 + 텍스트 검색(공고/회사/검색어/직군) + 정렬(최신/오래된/회사명)
- 카드: 출처 뱃지(색상) · 직군 · 검색어 · 위치 · NEW(게시일 7일 이내) · 게시일/마감일
- [🔄 전체 크롤링 실행] 버튼: POST /api/crawl → 3초 폴링 → 완료 시 자동 데이터 재로드
- Figma 캡처 스크립트가 `<head>`에 상주 (재캡처용)

| 항목 | 값 |

## 6. 에러 처리 정책

| 상황 | 처리 |
|---|---|
| HTTP 429 (LinkedIn) | 5초×시도횟수 대기 후 재시도, 3회 실패 시 해당 페이지 포기 |
| HTTP 400 / 결과 없음 | 해당 키워드 크롤링 조기 종료 (정상 흐름) |
| 요청 타임아웃 | saramin/work24 10~15초, linkedin 10초. 예외 시 해당 페이지 스킵 |
| 크롤링 중복 실행 | server.py가 409 반환 |
| 스케줄 실행 실패 | 슬랙으로 traceback 알림 + 프로세스 비정상 종료(스케줄러 이력에 남음) |
| 웹훅 미설정 | 알림만 생략, 크롤링/저장은 정상 수행 |

## 7. 제약 및 주의사항
- LinkedIn 게스트 API는 비공식 엔드포인트 — 응답 구조 변경 시 `linkedin.parse_jobs()` 셀렉터 수정 필요
- 사람인/고용24도 마크업 변경 시 셀렉터 유지보수 필요
- 크롤링 소요시간: 36키워드 × 10페이지 × 3소스 병렬 ≈ 20분 내외 (가장 느린 소스 기준)
- 이용약관 준수: 요청 간격 2초 유지, 개인 학습/구직 용도로만 사용
